## 3. 11 juillet — Modèle FSPL (commit `6b87464`)

**Objectif** : rendre la comparaison inter-bandes physiquement fondée. Le plafond de débit par
bande est dérivé de la perte en espace libre (FSPL) au lieu de valeurs arbitraires.

**Modèle** :
```
ΔPL = 20·log10(f_cible / f_réf)        f_réf = 2593,35 MHz (SSB n41)
K   = 10^(-ΔPL/10)
cap(bande) = K × plafond mesuré (Mbit)
```
Coefficients calculés en direct (jamais codés en dur) : n41 K=1,00 (100 %), n78 3499,68 MHz
K≈0,55 (55 %), n77 4173,60 MHz K≈0,39 (39 %).

**Fichiers ajoutés / modifiés** :
- `scripts/frequency/compute-fspl-k.sh` — calcul de K à partir des fréquences porteuses ;
- `scripts/frequency/apply-fspl-band-profile.sh` — applique le cap via `tc tbf + netem`
  (réutilise le mécanisme QoS des slices, bidirectionnel via `ifb_ue1`) ;
- `scripts/frequency/switch-ue-actual-frequency-retune-du-aware.sh` — variable d'environnement
  optionnelle `FSPL_CAP=1` : applique le cap après un retune réel de porteuse.

**Garantie** : comportement par défaut inchangé quand `FSPL_CAP` n'est pas défini.

### 5.3 Problème : KPI manquants dans la table « E2E Scenario KPI Results »

**Symptôme** (capture utilisateur) : « Image Download » affichait `—` pour
`throughput_mbps` et `time_s` ; « UDP Jitter/Loss » affichait `—` pour `time_s`.

**Diagnostic** :
1. Lecture des `summary.json` des runs du 10 juillet → **aucun champ KPI** : uniquement des
   métadonnées de job (`job_id`, `exit`, `log_file`…). Les KPI sont parsés du `output.log`
   à la volée par `_parse_job_kpis()` dans `scripts/traffic/traffic_api_server.py`.
2. Lecture des logs réels :
   - `run-udp-traffic.sh` imprime un résumé **texte** (`Throughput Mbps: 0.730114`) → parsé ✔,
     mais aucune ligne `Duration seconds:` → `time_s` = null ✘ ;
   - `run-image-download.sh` imprime un résultat **JSON** (`"throughput_mbps": 3.615046`,
     `"time_seconds": 1.529727`) → les regex texte (`Throughput Mbps:\s*…`) ne matchent
     jamais ce format ✘.

**Contrainte** : interdiction de toucher `scripts/` (les scripts de trafic et le serveur 5055
sont hors périmètre). **Solution** : nouveau blueprint même-origine dans le dashboard.

- **`web-dashboard/traffic_kpi_api.py`** (nouveau, 113 lignes) : route `/api/e2e-kpi/results`
  qui lit les mêmes répertoires de jobs (`~/oran-proof/phase2-traffic-api/`) avec des motifs
  **étendus** couvrant les deux formats :
  ```python
  k["throughput_mbps"] = first_non_none(
      last(r'(?:Average throughput|Throughput) Mbps:\s*([0-9.]+)', float),   # texte
      last(r'"throughput_mbps":\s*([0-9.]+)', float),                        # JSON
  )
  k["time_s"] = first_non_none(
      last(r'(?:Duration seconds|Transfer time seconds|...)', float),
      last(r'"(?:time_seconds|duration_seconds)":\s*([0-9.]+)', float),
  )
  ```
- `app.py` : `app.register_blueprint(traffic_kpi_bp)` ;
- `dashboard-inline.js` : `loadE2eKpiResults()` appelle `/api/e2e-kpi/results` au lieu de
  l'IP LAN codée en dur `http://192.168.1.142:5055` (bonus : plus de dépendance CORS).

  `time/action/ok` ; runs traffic-API : `finished_at/scenario/status`) ;
